# Composition failures and latency audit

Date: 13 September 2026. Investigation only; no application or hook changes.

## Conclusion

There is no single model-speed explanation. The evidence separates into a local provider-routing defect, a model-authored web-result handling defect interacting with mandatory research, upstream request failures, and expensive or broken synthesis programs. Successful delivery also does not establish that a model followed the research requirement.

## Scope and method

Inspected current server, settings, relay and hook sources; saved Studio versions; and their Codex session JSONL records. The selected 18 recent versions contain 16 OpenRouter attempts (four completed, four upstream 400 failures, four local 409 failures, four exhausted 429 failures) and two OpenAI attempts that stopped without composing. This is a recent incident sample, not a controlled model comparison or an estimate of the application's lifetime failure rate.

Turn elapsed time is task_started to task_complete. Tool time is the union of paired tool-call/output intervals, avoiding overlap double counting. It includes waiting and tool overhead, not just CPU execution. The remainder is not a measurement of model inference: it also includes network, scheduling and protocol time. Output-token totals likewise are not musical quality scores.

## 1. The quoted OpenAI refusal

The two runs used gpt-5.6-sol at low effort. Both ran with workspace-write, network_access:false and on-request approvals. They were classified as original generation, not incorrectly treated as source reconstruction.

The model called web search through this wrapper:

```js
const r = await tools.web__run(/* search request */);
for (const c of (r.content ?? [])) {
  if (c.type === 'text') text(c.text);
}
```

A read-only reproduction during this audit returned a nonempty string from web__run, not an object with a content array. The wrapper emits nothing for that return type. Consequently, blank displayed output is not proof that search found nothing. Historical underlying search responses were not emitted, so their contents cannot be recovered from these records. This is a model-authored tool-use error; no evidence shows Studio stripping the web result.

The subsequent curl calls really failed DNS resolution, but ran inside the network-disabled sandbox without an escalation request. That does not establish a host-wide DNS failure. Browser bootstrap separately returned “No browser is available.” These are three distinct observations, not corroboration of one global internet outage.

[resources/workbench-context.md](resources/workbench-context.md), line 7, requires research before composition. It says to report unavailable research, without a bounded recovery procedure. Although it does not literally say “stop composing,” the prerequisite was interpreted that way. The requirement originated in the requested workflow; silently making it optional would change that workflow. The first repair should make research execution and failure reporting reliable.

Evidence: session `01a0986a-253e-7570-b2a5-548d3cfbf4b6`, stored under the Codex sessions 2026/09/13 directory. Lines 22–25, 29–32 and 43–46 show the first turn's blank-producing search wrappers; 36–39 show curl failure; 65–68 show unavailable browser. Lines 91–94, 98–101 and 105–108 repeat these paths on retry. Turns lasted 76.4 and 27.5 seconds.

## 2. Provider changes can leave a loaded thread on its old endpoint

[server/index.mjs](server/index.mjs), lines 131–146, records the new provider selection but caches threads only by default versus OpenRouter. A loaded OpenRouter thread is not resumed with the new provider configuration. turn/start supplies the selected model, but not the updated endpoint configuration.

The relay guard at lines 160–163 compares the provider in the request URL with the newly selected active provider. Four attempts selected Modal, Novita or Fireworks while the thread still called the SiliconFlow URL. The local server returned 409 “No matching active provider turn.” Each ended in roughly 6.4–6.6 seconds with zero model tool calls and zero output tokens.

This is a demonstrated Studio defect. These failures are not evidence of slow inference or poor composition. Relevant version prefixes: 448c3534, f4bfda87, 5968cd19 and 940ffd0f; thread 01a09608-f890-7b30-baef-7a44b1872bb8.

## 3. Upstream failures are separate

Four selected attempts ended with upstream 400 “Server tool request failed”; returned metadata did not identify a serving provider. Four ended after exhausting retries on 429 responses. These establish request failures and rate limiting, respectively. The records do not establish the upstream internal cause, the limiting account or capacity pool, or whether another route would succeed.

[server/openrouter.mjs](server/openrouter.mjs) pins provider.only and disables fallback. It streams upstream response chunks with backpressure; it does not wait to buffer the entire response before displaying it. It has disconnect cancellation but no explicit upstream timeout. Neither this fact nor provider pinning alone proves the measured long turns were caused by the relay.

## 4. Long composition turns include substantial rendering and retry time

| Observed task | Total turn | Time inside tool intervals | Outcome |
| --- | ---: | ---: | --- |
| DeepSeek, five-minute Sugarplum | 28m 33s | 20m 40s | Upstream 400 |
| DeepSeek, piano continuation | 33m 11s | 26m 18s | Exhausted 429 |
| GLM, 100-second The Nine | 3m 19s | 22s | Completed |
| GLM, 100-second Neon Intersection | 7m 50s | 1m 49s | Completed after repeated code errors |

These tasks differ in duration, prior work and requested content. They cannot rank model speed. A later successful piano continuation also reused earlier work; it was not a fresh-generation comparison.

Sugarplum initially used generic signal.lfilter with long sparse delay coefficients on large audio arrays. The agent killed the slow renderer and replaced that path with blocked comb/allpass implementations. It also performed multiple full renders for verification. The trace includes waits of 180, 240 and 300 seconds. This is concrete synthesis-program execution and verification cost, not simply a model thinking for half an hour.

Evidence: session 01a09608-f890-7b30-baef-7a44b1872bb8, lines 115, 126–145, 149–168, 178 and 296–341. The original slow code is in the session history; the current renderer has already been changed.

## 5. The code errors are real

Neon Intersection contains 16 traceback-bearing tool outputs, not 16 independent root causes. They include:

- Invalid bandpass cutoff ordering.
- Mono/stereo and event-length array broadcasting mismatches, including repeatedly mismatched 13,230- and 9,702-sample buffers.
- Invalid lowpass/highpass cutoff values.
- A spb versus SPB name error.
- Missing scipy when using the wrong Python interpreter despite the supplied venv path.

Several fixes were followed by a whole-track render rather than a small failing-instrument check. Successful final delivery therefore hides substantial repair work.

Evidence: session 01a09695-42ad-7853-bd4d-e245cd930319, traceback outputs at lines 29, 38, 45, 59, 64, 69, 74, 79, 84, 89, 94, 99, 109, 118, 123 and 137.

## 6. Successful open-source runs did not demonstrate successful research

The inspected The Nine run has six tool calls and no recorded web retrieval or network-fetch command. Its notes nevertheless list research links and describe their influence. Neon Intersection also has no recorded web retrieval. This does not prove that the cited ideas are false; it means the required fresh research was not demonstrated in these traces.

Thus “it composed instead of refusing” is not evidence that the research tools worked for that model. The observed difference includes instruction compliance and reporting behavior, as well as engineering and composition ability. Both provider groups' inspected turn contexts used low effort and a network-disabled workspace sandbox.

## 7. Current telemetry cannot measure raw provider speed

Studio retains a flattened, truncated log rather than a durable timeline of tool calls and phases. Version records have creation times but do not preserve the complete timing breakdown. Token-usage notifications are not recorded by the server, and diagnostic stderr is not surfaced through a Studio listener. The underlying Codex JSONL logs were necessary for this audit.

Without request start, first token, completion, tool start/end and retry events, a long spinner cannot distinguish upstream latency, generated-code execution, retry backoff or a blocked prerequisite. The available data does not support “OpenRouter itself is the main reason composition is slow.”

## Repair order proposed, not implemented

1. Correct provider configuration when a selection changes on an already-loaded thread; regression-test a switch without paid inference.
2. Correct handling of web tool return types and distinguish empty results from discarded results. Preserve mandatory research, with explicit, bounded recovery and accurate failure reporting.
3. Record per-phase timings, retries, serving-route information and token usage; expose useful activity in the UI.
4. Encourage small instrument-render checks before whole-track runs and reuse tested numerical utilities without prescribing melodies, instruments or arrangement.

Do not add more artistic rules to address these failures. None of this audit establishes a musical-quality advantage for a model, and no production code or hooks were changed.
